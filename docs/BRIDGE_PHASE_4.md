# الدفعة الرابعة — RPC v2 وفصل أحداث الواجهة

## نطاق المنفّذ

هذه الدفعة لا تعني انتهاء كل فصل الواجهة. نُقلت عمليات Android غير المتزامنة إلى بروتوكول ذي معرّفات، وأزيلت المعالجات المضمّنة من شاشتَي الصوت/التسجيل ونافذة لصق النص وجزء إعدادات Vosk/المشاريع. ما زالت شاشات أخرى تستخدم globals وinline handlers، ومنها أزرار الضغط المطول وبعض الإعدادات والتقارير.

## 1. بروتوكول Android ↔ JavaScript

نقطة الدخول Native الجديدة هي `Daftari.dispatch(json)`. لا تقبل نص JavaScript أو مسار ملف من الواجهة. `bridge.js` وحده يصل إلى هذه النقطة.

طلب:

```json
{"version":2,"type":"request","id":"page-nonce-1","method":"model.import","params":{}}
```

ردود ممكنة:

```json
{"version":2,"id":"page-nonce-1","type":"progress","message":"جارٍ التحقق والاستيراد…"}
{"version":2,"id":"page-nonce-1","type":"success","data":{"kind":"vosk","files":12}}
{"version":2,"id":"page-nonce-1","type":"error","error":{"code":"IMPORT_FAILED","message":"فشل الاستيراد"}}
```

المعرّفات والأحجام هنا أمثلة توضيحية. لكل طلب رد نهائي واحد، وقد تسبقه رسائل progress. لا ترسل هذه الأمثلة رد نجاح وخطأ لنفس الطلب فعليًا.

### العمليات المسموحة

| method | data عند النجاح | المهلة الافتراضية في JS |
|---|---|---|
| `models.list` | `{version:1, models:[...]}`؛ مخطط البيانات السابق داخل غلاف RPC v2 | 10 ثوانٍ |
| `model.import` | `{kind:"vosk", files:N}` | 15 دقيقة، تشمل المنتقي والاستيراد |
| `project.import` | `{kind:"project", files:N}` | 15 دقيقة |
| `contact.pick` | `{name, phone}` | 3 دقائق، تشمل الإذن والمنتقي |

كل العمليات الحالية تقبل `params:{}` فقط. لا يمكن تمرير URI أو مسار وجهة. الحدود:

- معرّف بطول 1–80، أحرف لاتينية/أرقام/`_`/`-`.
- رسالة واردة Native بحد 8192 محرفًا؛ الرسائل المتجاوزة أو غير القابلة لربطها بمعرّف صالح تُهمل، ثم ينتهي انتظار JS بمهلته.
- 16 طلبًا معلّقًا كحد أقصى في كل طرف.
- تجاهل تكرار معرّف معلّق، والاحتفاظ بآخر 256 معرّفًا مكتملًا لمنع إعادة تنفيذه ضمن هذه النافذة. هذا ليس سجل idempotency دائمًا عبر إعادة التشغيل.
- التحقق من version وtype وmethod وparams في Android، ومن نوع الرد وبنية بياناته في JS.
- الردود تصل إلى `DaftariBridge.onResponse(frame)` بواسطة JSON مقتبس، لا بتركيب كود من حقول المستخدم.

## 2. واجهة JavaScript

```js
const task = DaftariBridge.pickModel({
  timeoutMs: 900000,
  onProgress: message => console.log(message)
});
// task.requestId
// task.cancel();
const imported = await task;
const models = await DaftariBridge.listModels();
```

`request()` وطرق الاختيار تعيد Promise، مع `requestId` و`cancel()` للطلبات الحديثة. يمكن تمرير `AbortSignal` كذلك. `listModels()` يعيد مصفوفة بعد التحقق من مخططها.

- الرد المتأخر أو المكرر أو الذي يحمل معرّفًا مجهولًا لا يؤثر على أي طلب آخر.
- progress لا يحسم Promise ولا يمدد المهلة تلقائيًا.
- تُنظف المؤقتات ومعالجات AbortSignal عند النجاح والفشل والإلغاء.
- انتهاء الوقت يُقاس أيضًا بالوقت الفعلي عند وصول الرد وعند عودة الصفحة للظهور، لا بالمؤقت وحده؛ WebView قد يعلّق مؤقتات الخلفية.
- `pagehide` ينهي الطلبات المحلية ويرسل إلغاءً بأفضل جهد. `daftari-background` لا يلغي RPC: منتقي Android نفسه يضع النشاط في الخلفية، ولا ينبغي أن يلغي الطلب الذي فتحه.
- لا توجد إعادة محاولة تلقائية لعمليات الاستيراد ذات الأثر على التخزين.

## 3. الإلغاء: ما يضمنه وما لا يضمنه

رسالة الإلغاء:

```json
{"version":2,"type":"cancel","id":"page-nonce-1"}
```

الإلغاء/timeout يحسم الانتظار المحلي أولًا، ثم يطلب من Android الإلغاء. **ليس ضمانًا للتراجع عن عملية اكتملت بالفعل**؛ رسالة الواجهة تنبّه إلى ذلك.

`RequestRegistry` يضبط الرد النهائي مرة واحدة ويستدعي callback الإلغاء. أما `OperationGate` فيحمي العملية الفعلية:

- إذا كان منتقي الملفات/جهات الاتصال مفتوحًا، لا تُحرّر خانته فور إلغاء Promise؛ يبقى مشغولًا حتى تعود نتيجته القديمة وتُستبعد.
- إذا كان الاستيراد يعمل، يُطلب interrupt من عامله. تبقى الخانة مشغولة إلى أن يخرج العامل من النسخ/التحقق/التثبيت والتنظيف.
- الإلغاء قبل بدء العامل محفوظ في lease ويطبّق عند دخوله، دون إسقاط مهمة مجدولة وترك حالة busy معلقة.
- يُمسح interrupt قبل إعادة استخدام thread في executor.
- نتيجة منتقي الاستيراد تُستهلك مرة واحدة؛ التكرار أثناء العمل لا يجدول استيرادًا ثانيًا.
- بوابة واحدة مشتركة لاستيراد النموذج والمشروع واختيار جهة الاتصال ضمن النشاط الحالي.
- لا محاولة لإغلاق تطبيق منتقي الملفات الخارجي قسرًا. على المستخدم إغلاقه إن بقي ظاهرًا.

العمليات المتوقفة داخل مزود ملفات بطيء قد لا تستجيب للـ interrupt فورًا. كما أن نقطة commit في التخزين تظل نافذة قد تنجح قبل وصول طلب الإلغاء؛ افحص قائمة النماذج قبل إعادة الاستيراد.

لا تُستعاد Promises عبر موت العملية أو إعادة إنشاء صفحة WebView. اختبارات إعادة إنشاء Activity وإرجاع نتائج المنتقي على جهاز فعلي ما زالت مطلوبة؛ بوابة النتائج الحالية مرتبطة بعمر النشاط وليست سجل عمليات Android دائمًا.

## 4. فصل المسؤوليات

- `bridge/RequestRegistry.java`: دورة حياة الطلبات، بلا Android أو JSON، ويمكن اختبارها على JVM.
- `bridge/AppBridge.java`: فك الغلاف والتحقق والتفويض للعمليات المسموحة.
- `bridge/JsCallback.java`: تسلسل الرد JSON وإرساله إلى WebView.
- `ui/OperationGate.java`: حجز المنتقي/العملية حتى انتهاء آثارها الفعلية.
- `ui/ImportCoordinator.java`: ربط نتيجة المنتقي بطلب محدد، العمل الخلفي، الإلغاء والرد.
- `ui/ContactPicker.java`: نتيجة منظّمة، وفشل واضح عند الرفض/الإلغاء/غياب جهة الاتصال.
- `ui/PermissionManager.java`: استدعاء نتيجة إذن جهات الاتصال في النجاح والرفض، بدل الصمت عند الرفض.
- `js/bridge.js`: النقل والمهل والتحقق فقط؛ لا كتابة إلى نموذج العميل ولا Toast مباشر.
- `js/native-actions.js`: رسائل المستخدم، عرض تقدم الاستيراد وزر إلغاء الانتظار، وتحديث النموذج الصحيح فقط.
- `js/model-catalog.js`: قراءة غير متزامنة، إلغاء القراءة القديمة وتجاهل نتائج render السابق.
- `js/ui-actions.js`: جدول أوامر محدد عبر `data-action`، دون `eval` أو البحث عن دوال عشوائية في window.

استقبال جهة اتصال متأخر لا يكتب في نموذج عميل آخر: تُفحص هوية النموذج والشاشة والحساب قبل التطبيق.

## 5. ترحيل أحداث الواجهة

- إزالة `onclick` من أزرار شاشتَي الصوت والتسجيل، بما فيها اختيار العميل وإعادة المحاولة.
- أسماء العملاء لا تُدرج داخل كود JavaScript؛ يمر معرّف العميل كسمة مقتبسة ومهربة ثم يُبحث عنه في البيانات.
- نافذة لصق النص تستخدم أسماء أوامر بدل التعبيرات المضمّنة.
- قسم Vosk وإجراءات المشروع في الإعدادات يستخدم التفويض، مع دعم Enter/Space للعناصر ذات role=button.
- تجاهل أوامر غير معروفة وعناصر disabled/aria-disabled والنقرات خارج حاويات التطبيق المحددة.
- إزالة تعريف `retryRec` قديم مكرر في `actions.js` كان يتجاوز تعريف مرحلة الصوت. أصبح retry يحتفظ بالعميل ولا يكدّس مسارات تسجيل إضافية.

**إغلاق أمني إضافي:** أزيل `document.write` الخاص باستيراد HTML في المتصفح. حزم HTML لا تُنفّذ داخل أصل يحتفظ ببيانات دفتر المستخدم. Android يستطيع حفظ ZIP كملفات خاملة؛ نسخة المتصفح تعرض رسالة بأن هذا الاستيراد غير متاح، بدل تشغيل كود الملف.

## 6. التوافق

- Native الجديد ينشر `dispatch` للعمليات غير المتزامنة، مع إبقاء طريقتَي القراءة القديمة `getModelList/importedList` فقط للتوافق.
- wrapper JS يستطيع التعامل مع Native قديم لا يملك dispatch. استيراد النموذج/المشروع القديم يبدأ العملية دون Promise يمثل اكتمالها؛ تعرض أحداث v1 القديمة النتيجة.
- جهة الاتصال القديمة تستخدم callback واحدًا. بعد إلغائه/انتهاء مهلته تُحجز الخانة حتى تصل النتيجة القديمة؛ إذا لم تصل أبدًا قد يلزم إعادة فتح الصفحة. لا يمكن توفير ضمانات v2 الكاملة عبر Native v1.
- التطبيق المجمّع الجديد يجب أن يستخدم أصول JS وNative الجديدة معًا؛ لا دعم لاستبدال صفحة APK الجديد بصفحة قديمة تستدعي طرق Native محذوفة مباشرة.
- أسماء التخزين وقواعد IndexedDB ومعرّف التطبيق لم تتغير.

## 7. نتائج التحقق

`npm test`: **40 اختبارًا ناجحًا**، موزعة على البنية والصوت والواجهة وRPC. الإضافات تغطي:

- الردود المعكوسة الترتيب والمكررة والمتأخرة.
- timeout وAbortSignal وpagehide والتوقيت بعد تعليق الخلفية.
- رفض الردود غير المطابقة والحد الأقصى للطلبات وفشل النقل.
- حجز callback القديم بعد الإلغاء.
- تجاهل بيانات نماذج أو جهات اتصال تخص واجهة قديمة.
- تفويض النقر على SVG داخل الزر، وحماية سمات العملاء، وعدم وجود handlers مضمنة في شاشة التسجيل.
- رفض الأوامر غير المعروفة/المعطلة، وأزرار لوحة المفاتيح.
- إلغاء الاستيراد من الواجهة دون إعلان نجاح متأخر، وعرض progress المحتوي على HTML كنص.

`tools/test-storage.sh`: نجحت مجموعات JVM الثلاث:

- StorageSafetyTest: 1045 تحققًا، معظم العدد فحوص TAR بايتًا بايتًا.
- ImportLifecycleTest: 46 تحققًا.
- BridgeLifecycleTest: 38 تحققًا، تشمل الرد مرة واحدة، التكرار، السعة، إغلاق الطلبات، حجز المنتقي، وinterrupt العامل.

نجح تجميع مصادر Android مقابل API 35 عبر أداة الفحص السابقة، مع 3 تحذيرات deprecation المعروفة. **لم يُبنَ APK، ولم تُنفّذ اختبارات Instrumentation أو منتقي Android فعلي.** اختبارات RPC في JS تستخدم Native وهميًا؛ اختبارات Registry/Gate على JVM حقيقية لكنها لا تحاكي نظام Android نفسه.

## المتبقي

- فصل بقية شاشات وقوالب UI وinline handlers، وتقليل globals وتوحيد حالة التطبيق.
- مخطط مشروع بيانات الدفتر وترحيلات التخزين متعددة الإصدارات؛ حزمة HTML الخاملة ليست بديلًا عنه.
- تدقيق استيراد بيانات الدفتر ومواضع HTML الديناميكي الأخرى؛ لم يُدّعَ تدقيق XSS شامل.
- اختبار Activity recreation/موت العملية أثناء المنتقي على Android، وحدود صلاحيات ContentResolver.
- تشغيل المحركات الحقيقية وبناء APK واختبارات Android 5/14 والشاشات قبل الإصدار.
