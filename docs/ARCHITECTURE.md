# بنية دَفتَري 3.0 — Architecture

> هذا المستند يشرح **لماذا** بُنيت النسخة 3.0 بهذه الطريقة، وكيف تُextend
> بها في المستقبل دون لمس النواة.

---

## 1. المشكلة التي حُلّت

النسخة 2.22 كانت صفحة واحدة `index.html` بحجم 2.1 ميغابايت و14,025 سطرًا:
CSS مضمّن، ستّ مكتبات طرف ثالث مضمّنة، ومنطق التطبيق كاملًا في كتلة واحدة.
لا يمكن اختبار أي جزء منها بمعزل، ولا يمكن تحديث جزء منها دون استبدال
الملف كاملًا، وأي سطر جديد يسبّب صراعًا في كل دفعة.

**الهدف:** واجهة معيارية قابلة للاختبار، نظام مقاسات واحد، مسار تحديث
حقيقي، ونقطة توسّع مفتوحة — **دون تغيير أي سلوك موجود**.

| الضمان | كيف تحقّق |
|---|---|

| لا فقدان بيانات | نفس الشيفرة، ونفس ترتيب التنفيذ، ونفس مخطط التخزين |

## 3.طبقات الواجهة

```
index.html (6 KB)
   ├── css/tokens.css      ← الرموز (اللون + القياس) — يجب أن تأتي أولًا
   ├── css/base.css        ← التصفير والأنواع
   ├── css/components.css  ← العناصر
   ├── css/layout.css      ← الهيكل
   ├── css/responsive.css  ← المقاسات المتكيّفة (تستهلك الرموز)
   ├── js/00 … 99          ← 44 وحدة، ترتيبها من بادئة اسم الملف
   └── lib/                ← 6 مكتبات، تُحمَّل كسولًا عبر libLoad()
```

**لماذا سكربتات كلاسيكية وليست ES modules؟** الواجهة تعتمد على معالجات
`onclick` المضمّنة داخل نصوص HTML،These تحتاج أسماء في النطاق العام. الوحدات
الكلاسيكية تتشارك النطاق العام فتحتفظ.وسوم `onclick` تعمل كما كانت
بالضبط.

**لماذا ترقيم الملفات؟** بادئة الرقم هي ترتيب التحميل، و`web/build.mjs`
يولّد قائمة `<script>` تلقائيًا من محتويات المجلد — فإضافة وحدة جديدة لا
تتطلب لمس `index.html` إطلاقًا.

## 4. نظام المقاسات

المبدأ: **القيم تقرأ من مكان واحد**.

```
tokens.css
  --s: 1            ← حجم الواجهة (0.85 – 1.40)
  --density: 1      ← الإيقاع الرأسي (0.88 – 1.12)
  --sp-1..8         ← سلّم المسافات
  --h-btn, --ic-md  ← ارتفاعات العناصر ومقاسات الأيقونات
  --fs-*            ← سلّم الخطوط

responsive.css
  .btn { height: calc(var(--h-btn) * var(--s)); }
  .litem { padding-block: calc(10px * var(--s) * var(--density)); }
```

`js/71-appearance.js` يكتب `--s` و`--density` على `:root` من تفضيل
محفوظ في `localStorage`، **قبل أول رسم** — فلا وميض.

الحدود مطبَّقة في الكود (`clampScale`, `clampDensity`) وليس في CSS وحده،
فتكون القيمة المعروضة في الواجهة مطابقة تمامًا للقيمة المطبَّقة.

## 5. نظام التحديث

### 5.1 الحزمة

حزمة الواجهة ملف ZIP عادي يحوي `version.json` + الشجرة كاملة. الـ manifest
يصف كل ملف بحجمه وبصمة SHA‑256، فيمكن إثبات نزاهتها من أي طرف.

### 5.2 التحقق المزدوج

| الطبقة | ما تفعله |
|---|---|
| المتصفح (`72-update.js`) | تقرأ الـ ZIP (بلا مكتبة، عبر `DecompressionStream`)، تتحقق من البصمات، ترفض مسارات `..` |
| الجهاز (`UpdateInstaller.java`) | تفك الضغط في `webroot.staged`، تتحقق من البصمات، ترفض أي ملف غير معلَن عنه |

### 5.3 التفعيل والرجوع

```
webroot/         ← الباقة الفعّالة الآن
webroot.staged/  ← باقة مُثبَّتة تنتظر التفعيل
webroot.prev/    ← الباقة السابقة (للرجوع)
```

- `activate()` تنقل `staged → overlay` وتحفظ `overlay → prev`.
- `rollback()` تعيد `prev → overlay`.
- أي فشل أثناء التثبيت يحذف `staged` فقط، والإصدار الجاري لا يُمَس.

### 5.4 أولوية تقديم الملفات

```
1. ما استورده المستخدم (نماذج، مشاريع، محرك Vosk)   ← اختيار صريح
2. الباقة المثبَّتة (update overlay)
3. الأصول داخل الـ APK
```

الأولوية الأولى تحفظ عادة المستخدم (استيراد محرك Vosk مخصّص)، والثانية
تجعل التحديث يعمل فعلًا، والثالثة هي خط الأساس.

## 6. طبقة Java

| الصنف | المسؤولية |
|---|---|
| `MainActivity` | الربط ودورة الحياة فقط |
| `web.WebAssetServer` | تقديم الملفات من الأصل الافتراضي الآمن |
| `web.WebRoot` | إدارة مجلدات الباقة وmanifest |
| `web.WebPaths` | منع الخروج عن الجذر (zip-slip والمسارات المطلقة) |
| `update.UpdateInstaller` | فكّ، تحقّق، تفعيل، رجوع |
| `model.ModelImporter` | استيراد نماذج Vosk والمشاريع (zip + tar.gz) |
| `bridge.NativeBridge` | جسر `Daftari` — pickVosk / pickProject / importedList / pickContact |
| `bridge.UpdateBridge` | جسر `DaftariUpdate` — pickUpdate / activate / rollback / reload |
| `util.Json` | قارئ JSON بلا اعتماديات |
| `util.Sha256` | بصمات SHA‑256 |

**لماذا قُسِّم الـ monolith؟** لأن `MainActivity` كان god-class يفعل ستّة أشياء
متباينة. الفصل يجعل كل جزء قابلًا للاختبار وحده، ويفصل ما يمكن أن يتعطّل
(استيراد نموذج) عمّا لا يمكن (تقديم الواجهة).

### جسر التحديث

`DaftariUpdate` يعمل بنصفين لأن اختيار الملف غير متزامن:

```js
DaftariUpdate.pickUpdate();                       // يفتح منتقي الملفات
// … Later، بعد اختيار المستخدم:
window.__dafterUpdateResult({ok: true, version: "3.1.0", …});
```

`activate()` و`rollback()` متزامنان (تبديل مجلدات) فيردّان JSON مباشرة.

### ما لم يُتحقَّق منه

- **بناء الـ APK**: لا JDK ولا Android SDK في بيئة البناء، فلم يُنفَّذ
  `gradlew assembleDebug`. التحقق من Java تحليلي (نحوي) لا تصريحي.
- **سلوك WebView الحقيقي**: الاختبارات تعمل داخل jsdom، وهو يقلّد DOM
  있지만 لا ينفّذ WebAssembly ولا الكاميرا ولا الميكروفون.
